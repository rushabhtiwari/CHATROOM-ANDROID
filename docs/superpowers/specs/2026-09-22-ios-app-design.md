# iOS App — Chats and Order Tracking

**Date:** 2026-09-22
**Status:** Approved
**Scope:** Sub-project #4 of four (see Decomposition)

## Summary

A hybrid iOS app delivering two KiranOS features — the conversation
workspace and sales-order/dispatch tracking — as a Capacitor + Vite +
React application. The mobile UI is written for the phone; the domain
logic is imported unchanged from the existing console.

## Decomposition

"Real backend for chats and orders" is not one project. It is four,
with a strict dependency order. This spec covers #4 only.

| # | Sub-project | Depends on |
| --- | --- | --- |
| 1 | Identity wiring — KiranOS authenticates against the existing OIDC service | — |
| 2 | Chat backend — persisted messages, WebSocket fan-out, real transport | 1 |
| 3 | Orders backend — orders/dispatches move from mock arrays to real endpoints | 1 |
| 4 | **iOS app** — this spec | 1, and 2/3 for live data |

#4 is built first, against today's mock and local data, behind an API
seam (section 4) so that #2 and #3 land as configuration rather than a
rewrite.

## Findings that shaped the design

1. Both features live in `modules/kiran-payment/master-frontend/vd`
   (KiranOS) — Vite 6, React 18, react-router 6, Tailwind 3, Radix —
   not in `portal/` (Next.js). The mobile app matches KiranOS.
2. Neither feature has a backend. Chat persists to `localStorage` via
   `lib/chat-persistence.ts` and sends through `lib/transport.ts`, a
   *simulated* network. Orders and dispatches are hardcoded arrays in
   `src/data/orders.ts` and `src/data/dispatches.ts`.
3. KiranOS has no authentication. The current user is selected from a
   seeded directory; `modules/rts/identity.ts` documents the name-based
   join as "demo-grade".
4. `useChat()` exposes ~120 methods with no DOM assumptions. The chat
   domain is already a reusable, UI-agnostic layer.
5. The console reaches the server through same-origin relative paths
   (`/api`, `/uploads`) served by the Vite proxy. Capacitor serves from
   `capacitor://localhost` and has no proxy, so this must change.

## 1. Repo layout

`modules/kiran-payment/` becomes an npm workspace with two members.

```
modules/kiran-payment/
  package.json              workspace root
  master-frontend/vd/       existing console — one key added
  mobile/                   the iOS app
    capacitor.config.ts
    vite.config.ts
    ios/                    generated by cap add ios, committed
    src/
      App.tsx main.tsx      router + providers
      screens/chat/
      screens/orders/
      components/           mobile primitives
      native/               Capacitor adapters
      api/                  the origin seam
```

The only change to the console is an `exports` key in its
`package.json`. No file moves, no import rewrites.

## 2. Shared vs. new

Imported from `kiran-os` unmodified:

| Module | Purpose |
| --- | --- |
| `lib/chat-store` (`ChatProvider`, `useChat`) | The whole chat domain |
| `lib/chat-types` | Types |
| `lib/transport` | The swap seam for sub-project #2 |
| `lib/mentions`, `attachments`, `time`, `utils` | Domain helpers |
| `data/orders`, `data/dispatches`, `types/` | Order and dispatch model |
| `modules/rts/*`, `modules/calendar/*` | Claims and meetings |

Written new: every screen and component. Not reused:
`ConversationSidebar`, `ContextPanel`, `CommandPalette`, `DataGrid`,
`DispatchBoard`, the dialog set — all desktop-shaped.

`ClaimCard` is ported rather than rewritten; its logic already reads
from the server on each render.

## 3. Screens

Four bottom tabs: Chats, Orders, Dispatches, Me.

**Chats** — `ChatListScreen` (rooms and DMs, unread from `unreadFor`),
`ConversationScreen` (virtualised list, long-press reactions, reply,
markdown, pinned banner, jump-to-message), `ThreadScreen` (a pushed
route, not a side panel), `ComposerSheet` (mentions, attachments,
agent), `AgentSheet`, `ClaimCard`, `MeetingFlowScreen`.

**Orders** — `OrdersScreen` (searchable cards; executed/balance
progress from `executedQty`/`poQty`), `OrderDetailScreen` (segmented:
`weeklyBuckets` / `workOrders` / `dispatches`).

**Dispatches** — `DispatchesScreen` (grouped by `stage`, filter chips),
`DispatchDetailScreen` (vertical timeline over the six `stage` values,
carrier, vehicle, destination, `podStatus`, and a
`stopDispatchBlocked` banner).

**Me** — current user (`setCurrentUserId` until #1 lands), notification
settings, online toggle, storage status.

Order tracking is read-only. Writes wait for sub-project #3.

## 4. The API origin seam

`mobile/src/api/origin.ts` is the one place that knows where the server
is. It reads `VITE_API_ORIGIN`, defaulting to the empty string: empty
on web (relative paths, proxied as today), a real host on device.

**Amended during implementation.** This section first proposed an
`apiFetch` wrapper plus a one-line change to `modules/rts/api.ts`. The
code had more call sites than that: six, across three console files
(`fetch('/api/agent')` and `/api/meet` in the chat store, every call in
`modules/rts/api.ts` and `modules/calendar/api.ts`, and the live-update
stream opened with `new EventSource('/api/events')`), plus receipt links
the server returns as `/uploads/...`. Editing each would change the
console for the phone's sake and miss the next one added.

Instead `mobile/src/api/install.ts` wraps `fetch` and `EventSource` once
at startup and rewrites only relative `/api` and `/uploads` paths —
matched as whole segments — to the configured origin, with credentials.
The app's own assets, absolute URLs, `blob:` and `data:` pass through.
With no origin configured nothing is installed. The console is not
modified.

FastAPI allows CORS for `capacitor://localhost` (done in
`backend/app/main.py`).

This seam is also how #2 and #3 arrive without touching the UI.

## 5. Data flow

Screens call `useChat` and `useOrders`, which read the `kiran-os`
domain layer. Chat sends flow through the simulated transport; the
agent, receipts, claims and meetings flow through the installed
redirect to `API_ORIGIN`. Snapshots persist through Capacitor Preferences.

`chat-persistence.ts` writes to `localStorage`, which iOS WKWebView
evicts under storage pressure. The mobile app injects a
`@capacitor/preferences`-backed storage adapter: same schema, same
migration path, different sink.

## 6. Push notifications

v1 ships the plumbing, not fake pushes: permission flow, APNs token
registration, a `native/push.ts` adapter, deep-link routing (a message
notification opens that conversation; a dispatch notification opens
that dispatch), and local notifications driven by the existing in-app
notification feed.

Server-sent push is a dependency on #2 and #3 and is out of scope here.

## 7. Error handling

`outbox` drives a per-message sending/failed state with tap-to-retry
and discard. `online` binds to `@capacitor/network`, so airplane mode
replaces the simulated toggle. `storageStatus` and
`reclaimAttachmentSpace` drive a storage banner. Failed server calls
degrade exactly as the console degrades — the agent reports it has no
model, receipt reading falls back to manual entry. Nothing dead-ends.

## 8. Build and verification

Development is on Windows; iOS compilation is not possible there.

Windows-doable: the whole web app, Capacitor config, the `ios/`
platform folder, and the full mobile UI verified in a browser at
390x844.

macOS-gated, delegated to a GitHub Actions `macos-latest` runner:
CocoaPods install, `xcodebuild`, Simulator runs, archives. APNs
certificates and device testing additionally need an Apple Developer
account.

Testing: Vitest and Testing Library over mobile screens against a
mocked `useChat`. Domain logic is not re-tested — it lives in
`kiran-os`. Playwright e2e is deferred until a real backend exists.

## Out of scope

Real authentication, real chat server, real orders API, order writes,
Android, App Store submission.
